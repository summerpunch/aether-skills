# 将规约落实到方案和代码

按任务规模使用本流程。此文件指导规约应用，不授予修改项目的权限。小范围修复可以简化记录，但仍需核对相关【强制】项；跨模块、新 API、数据变更或并发改动应留下可追踪的规则与验证证据。

## 一、发现和设计

1. 确认目标：预期行为、不可改变的接口/数据契约、Java 版本、项目框架、已有包结构、测试和质量门槛。检查同类实现，理解现有抽象与异常/日志/事务习惯。
2. 画出变更影响：入口、业务规则、持久化、远程依赖、状态变化、用户可见错误、安全边界与回滚路径。只为复杂交互绘制必要的状态/时序/活动图，并把设计约束记录到现有文档机制。
3. 建立适用规则清单。建议只记录三列：**规则编号及等级**、**实现位置/设计决定**、**验证方式**。先查 `rulebook/INDEX.md`，再查对应章的小节；不要靠本文件的摘要替代逐条阅读。
4. 作出方案选择时，先比较正确性、兼容性、安全、资源上限和可测试性，再看性能与代码量。设计方案应明确输入、输出、失败语义、事务/幂等、时间与金额表示、数据生命周期、权限及远程超时。

## 二、告知用户并确认方案

在修改项目文件前，提交可审阅的具体方案：预期改动及涉及文件、依据的关键规约、对现有行为和调用方的影响、测试与验证办法。等待用户明确确认；未确认时仅继续只读分析和方案完善。用户已经在本次工作中确认同一具体方案的，无需重复询问。实施中若需扩大文件范围、改变对外契约或变更关键设计，先更新方案并再次确认。

## 三、确认后的编码和重构

- 先确定最小可维护改动范围，再实现行为。命名、格式、OOP、日期、集合、并发和注释按编程规约对应小节核对；DTO/DO/JSON/SQL 的命名与类型要同时对齐。
- 新建或整理 Java 源文件时，按 `google-java-style-supplement.md` 核对源码结构、导入和声明；只应用其中列出的补充条款，保持阿里格式要求。
- 外部输入在边界验证；资源操作在执行前鉴权；错误在合适层转义；事务中的异常不可被吞掉；日志保留定位线索并避免敏感数据。SQL 参数绑定，索引与查询形状一致。
- 对共享状态、线程池、连接池、批处理和缓存设清晰容量/生命周期；出现重试时考虑超时总预算和幂等性。远程弱依赖要有预期失败策略。
- 复用现有框架和依赖。新增接口、层、通用工具、常量或配置应有实际边界价值；不要以“遵守规范”为由扩大重构范围。
- 如果手册原文与现有契约或现代运行环境有冲突，记录触发条件、原规则要防范的风险和等效控制措施。不能单凭“过时”二字跳过规则。

## 四、验证门槛

| 变更 | 至少核对 |
| --- | --- |
| 纯 Java 逻辑 | 编译、相关单测、空值/边界/异常路径、相关编程规约 |
| API/Controller | 参数与权限、请求/响应兼容、错误码与状态码、序列化、相关测试 |
| 数据库 | 迁移可回滚、字段映射、唯一约束、索引与执行计划、事务及并发更新 |
| 并发/远程调用 | 资源上限、超时、拒绝与关闭、竞态/死锁、失败恢复 |
| 安全敏感 | 对象级授权、注入与输出编码、秘密和日志脱敏、滥用/重放边界 |

运行仓库现有的格式化器、编译器、相关测试及已配置的静态检查（包括已接入的 p3c）。扫描只能覆盖部分可机器判断的条款；对安全、SQL 性能、架构和业务语义仍需人工核对。不要为了本流程自行修改 CI 或安装插件，除非当前任务要求。

## 五、评审与交付

- 评审按影响排序：安全/数据损坏/不可用、外部契约或并发缺陷、性能与可维护性、格式。每个发现写明代码位置、触发条件、实际后果、规约编号和等级、建议修复。没有证据的偏好不列为发现。
- 方案评审说明关键设计决定、适用的强制规则、显式偏离、测试与回滚办法。没有实际修改代码时，不声称已通过编译或测试。
- 交付代码时报告改动和执行过的验证；对未能验证的路径写出具体限制。所有适用【强制】项应能对应到实现或清楚解释的不适用条件。
