# MySQL、依赖与设计

本文件是[MySQL 数据库](rulebook/05-mysql.md)、[工程结构](rulebook/06-project-structure.md)与[设计规约](rulebook/07-design.md)的应用指引。这些规则大多依赖数据库版本、部署规模与现有契约；先确认实际技术栈，完整条文与等级以规约正文为准。

## Schema 和索引

- 【强制】表和字段名小写，避免保留字；业务唯一性由唯一索引兜底。数据库字段类型与 Java DO 属性匹配，金额/精确小数用 `DECIMAL` 或经设计确认的最小货币单位整数，不用浮点字段保存精确值。
- 手册要求 `is_xxx` 布尔列、`id/create_time/update_time`、逻辑删除和索引名前缀 `pk_/uk_/idx_`。新表按这些约定设计；已有表或跨数据库项目先检查迁移、唯一性、审计和兼容成本，必要偏离应记录。逻辑删除必须一并考虑唯一索引、查询过滤、保留期限和隐私删除要求。
- 【强制】页面搜索的左/全模糊若无法利用普通 B-tree 索引，选择合适的全文索引或搜索服务；关联字段类型一致且必要时有索引。索引顺序依据实际 `WHERE`、`ORDER BY`、数据分布和执行计划确定，不盲从固定“选择性最高在最左”口号。
- 【推荐】大分页可用游标/键集分页或经验证的延迟关联；分库分表根据增长预测和运维成本决定，不把手册的 500 万行/2GB 示例当自动触发阈值。

## SQL 与 ORM

- 【强制】查询明确列名，不用 `SELECT *`；多表查询列加表别名；`COUNT(*)` 用于统计行数，注意 `COUNT(col)` 忽略 `NULL`、`SUM` 可返回 `NULL`。对可空列使用 `IS NULL`/`IS NOT NULL`，不要使用 `= NULL`；手册的 `ISNULL()` 示例与其反例文字存在表述歧义，按正确 SQL 语义和目标 MySQL 的执行计划判断。
- 【强制】MyBatis/iBATIS 值绑定用 `#{}`，不要用 `${}` 直接接收外部值；标识符只能来自受控白名单。布尔列和 POJO 属性做明确映射，更新记录时维护 `update_time`。避免无条件全字段更新覆盖并发修改。
- 【强制】变更数据前核实目标范围，批量更正先用同条件查询核对并准备回滚。事务边界要覆盖需要原子化的数据库操作；外部消息、缓存、搜索索引不能假设随数据库事务自动回滚，需设计补偿/幂等。
- 手册禁止外键/级联与存储过程，源于高并发分布式场景。若现有系统依赖数据库约束或迁移成本高，先保持一致性并记录与阿里严格规约的差异，不删除现有约束以追求形式合规。

## 工程与设计

- 【强制】依赖版本统一，升级二方库时核对传递依赖冲突及兼容性，不依赖不稳定的 SNAPSHOT 发布物。只在受影响范围内改依赖图。
- 【推荐】层次职责清楚：入口负责协议/鉴权/参数边界，业务层承载规则，数据层处理持久化；具体层数和名称遵循仓库已有架构。对外部依赖设置超时与隔离，标识核心链路和弱依赖的降级方式。
- 【强制】存储方案与底层数据结构应在项目的设计评审机制内审查；复杂状态、对象协作和调用链用能准确表达约束的图或文档。手册规定的图例阈值用于提醒复杂度，日常小改动不凭数量机械生成图。
- 【推荐】模块边界、错误流程和非功能需求要可解释；优先组合和清晰接口，避免重复业务逻辑，同时避免过早抽象。
