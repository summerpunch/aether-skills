# Java 开发规约

本 skill 自带黄山版 1.7.1 的完整分章规约、说明、正反例、术语和错误码目录。使用时只读取本目录的 `SKILL.md` 与 `references/`；不依赖 `source/` 文件或网络资料。

**本 skill 是代码规约，不构成实施授权。** 可以先只读检查项目、评审代码并拟定方案。基于本 skill 新增、修改或删除 Java 项目文件（包括测试、配置和数据库迁移）前，先向用户说明具体改动范围、适用规约、行为与兼容性影响、验证办法，等待用户明确确认方案。确认后只在已确认范围内实施；方案发生实质变化时重新告知并确认。若用户此前已经确认了同一具体方案，无需重复确认。

## 规则和判断方式

- **规约正文**见 [规约目录](references/rulebook/INDEX.md)。规则编号按“章－节－条”识别，例如“一（七）4”。【强制】为适用场景的合规要求；【推荐】需结合收益与成本；【参考】用于设计判断。补充实践单独标明，不能冒充原规约。
- 新建或整理 Java 源文件时，再读 [Google 源码风格补充](references/google-java-style-supplement.md)。它仅补充与阿里规约不冲突的源码布局、导入及声明规则；用 `GJ-xx` 编号标识，不改变阿里缩进、行宽或 Javadoc 要求。
- 用户要求、目标仓库的 `AGENTS.md`、已经对外承诺的接口/数据契约与实际运行环境必须先确认。发现这些约束与规约冲突时，说明具体条款、影响和处理选择；不要悄悄忽略【强制】项，也不要为了形式合规破坏既有行为。
- 黄山版发布于 2022 年。涉及 Java 17/21、虚拟线程、`record`、框架托管线程池、云原生日志、数据库迁移或安全控制时，先判断原规则要防范的风险，再按当前技术栈实现等效保障。三个应用指引只补充判断，完整规则仍以规约正文为准。

## 执行流程

1. **建立上下文**：检查仓库说明、Java 版本、Maven/Gradle 构建、框架、格式化/静态检查配置、相邻实现、公开契约及已有测试；确定本次是方案、编码、重构还是评审。
2. **圈定适用规则**：按下表打开相关规约章节，检索并逐条核对涉及的【强制】项。复杂任务建立简短的“规则－实现位置－验证证据”清单；不相关章节不用加载。
3. **提交方案并等待确认**：先明确输入/输出、数据与状态、授权、失败和并发边界，再向用户说明拟改文件、关键设计、相关规约、兼容性影响与验证办法。未确认前保持只读。完整操作方法见 [工作流程](references/workflows.md)。
4. **确认后实施**：在已确认范围内按规约写代码并补充能验证行为的测试。
5. **验证**：使用仓库已有的格式化、编译、相关测试与静态检查；人工复核自动工具难以判断的授权、事务、索引、超时、资源上限与兼容性。只报告确实执行过的检查。
6. **交付或评审**：说明实现及验证结果。发现问题时给出文件/行号、触发条件、影响、修改建议和规约编号/等级；“高风险”与“【强制】”是不同维度，不混用。

## 收尾核对

- 项目文件的改动已有用户对具体方案的确认，且实际改动未超出确认范围。
- 新代码与相关【强制】条目一致；不适用或冲突的条目有具体理由。
- 对外契约、数据库迁移和已有调用方的行为保持可解释；安全与异常路径经过验证。
- 测试覆盖主要行为、边界与失败条件；格式、编译、测试和已有扫描结果有据可查。
- 方案和评审能从规则编号追到实现或问题位置；不以工具扫描“通过”代替人工核对。
